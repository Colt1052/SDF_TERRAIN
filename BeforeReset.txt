● You're broadly right on the intuition — there's a real opportunity here, but
  the "solid air" case has a subtlety worth thinking through before
  implementation.

  Why it works for solid terrain

  When an edit is deep in solid terrain (SDF << 0, say < -0.1 or some
  threshold), baking it into the base is low-risk:

  - No surface to perturb. The zero-crossing is far away, so floating-point
    noise in the baked value can't shift the boundary into visible error.
  - Edits in solid are usually subtractive (carving tunnels, caves). You're
    replacing min(base, edit) with a new base that already encodes the carve.
    Since both values are large negatives, min() is well-behaved numerically.
  - Irreversible by nature. Once carved, that region stays carved unless
    explicitly filled back in — which would be a new edit that starts fresh.

  The solid air case is trickier

  When an edit is deep in air (SDF >> 0), adding terrain (like painting a
  mountain peak or bridge) into empty space:

  - The edit itself creates a new surface. You're not just modifying an existing
    boundary — you're introducing new geometry with its own zero-crossing.
    Baking this means committing that new surface into the base SDF as if it
    were "natural" terrain.
  - This is fine if the edit is self-contained — i.e., the entire edit including
    its surface is in a region you're baking. The floating-point precision of
    the base SDF evaluation just needs to be good enough to represent that new
    surface.
  - The concern arises at the edges of the edit brush. If a brush stroke extends
    into a region where the base SDF is also non-zero (say, you paint a ridge
    that connects to existing terrain), the blend zone needs to be baked too. If
    you only bake the "clearly air" portion, you get a seam.

  The real threshold question

  The practical design is:

  ▎ An edit is bake-eligible when, over the entire spatial extent the edit 
  ▎ affects, the resulting SDF surface is unchanged AND the edit's influence is 
  ▎ below some epsilon everywhere near any existing surface.

  Concretely, for a volume cell or region:
  - If |resulting_SDF| > threshold everywhere in the region (no zero-crossing
    inside), and
  - The edit contributed to that region

  ...then that region can be baked. The threshold should be comfortably larger
  than floating-point noise (e.g., 0.01–0.05 world units, depending on your
  scale).

  What I'd recommend

  1. Start with solid-only baking. Carved tunnels and caves are the most common
     repetitive edits, and they're the safest case. Get the infrastructure
     working here first.
  2. Define a "bake threshold" as a configurable parameter — not hardcode it.
     Something like minimumDistanceFromSurfaceToBake = 0.05f.
  3. Bake at evaluation time, not edit time. When you evaluate the SDF for
     meshing (or for a cache/volume), if a cell's edit contribution is in the
     bake-eligible zone, write it into a persistent base cache rather than
     keeping it in the edit list. Then remove it from the live edit list.
  4. Handle the "edit undoes another edit" case. If edit B fills in what edit A
     carved, and A hasn't been baked yet, cancel both. Don't bake intermediate
     states.
  5. Deferred baking. Don't bake immediately. Let the user keep editing. Bake
     during idle moments or when the edit list exceeds some size threshold. This
     avoids committing geometry the user might soon modify.

  Bottom line

  Yes, floating-point precision is not the problem you think it is — it's only a
  problem near the zero-crossing, and by definition you're avoiding those
  regions. The real challenges are:
  - Seam management at the boundary between baked and unbaked regions
  - Edit lifecycle (undo, overlapping edits, edits that modify already-baked
    regions)
  - Choosing the bake threshold so you don't lose detail

  this would fit?

● Ah, now I see — this is edit garbage collection, not baking in the geometric
  sense. You're right, and it's a cleaner problem than I initially thought.

  Two removal cases

  Interior edit (buried): A building edit is now entirely encapsulated by solid
  terrain. The base SDF (or a later, larger building edit) dominates everywhere
  in that region. Removing it changes nothing because min(base, buried_edit) = 
  base everywhere that matters.

  Exterior edit (enveloped): A small mining edit is now entirely inside a larger
  mined-out cavity. The larger edit already made everything air. Removing the
  small edit changes nothing because min(large_mine, small_mine) = large_mine
  everywhere.

  In both cases the edit is a no-op — it doesn't affect the composite SDF at
  all. Removing it is free and lossless.

  The "bake" language

  For the interior case, "bake into the SDF" is accurate — the base SDF already
  describes that region, so dropping the edit just lets the base take over.

  For the exterior case, there's nothing to bake — you're just deleting a
  redundant entry. The dominant edit (the bigger mine) already handles the
  geometry.

  So really: scan the edit list, identify no-ops, delete them.

  The practical questions

  Threshold: You need a cleanupDepth parameter — how deep in solid/air before an
  edit qualifies. E.g., every point the edit affects must have |final_SDF| > 
  cleanupDepth AND the edit must not be the reason for that value.

  Safety with undo: This is the real gotcha. If you purge an old mining edit
  because a newer one envelopes it, then the user undoes the newer edit — the
  old one is gone and should come back. Either:
  - Only purge after undo history is truncated (e.g., user saves/checkpoints)
  - Or track purged edits per region and restore them if a dominating edit is
    undone

  When to run: Not every frame. Run during idle, or when the edit count crosses
  a threshold, or explicitly triggered.

  How to check: For each candidate edit, sample the SDF over its spatial extent
  (excluding that edit from the composite). If every sample shows the edit has
  no effect on the result → safe to remove.

  Verdict

  Solid idea. The math is straightforward — you're removing identity elements
  from a min-composition. No floating-point issues because you're not changing
  any geometry. The implementation work is in the spatial checking, the undo
  safety, and deciding when to run the sweep.
